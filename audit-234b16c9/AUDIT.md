## 2. Механика харнеса: что ломается на долгом запуске

### 2.1. Гонка `Edit`/`Write` по одному пути — потеря данных

**Факты.** 722 Edit. В 36 ходах модель посылала ≥2 Edit в один файл одним ответом (как её и просит
преамбула — «go wider with tool calls»). В 39 случаях позже накатывалась правка с тем же `path` и тем же
`old_string`, что и ранее «успешная» — т. е. первая не дошла до диска. Модель это заметила в 00:11 («Edits
were silently lost (last writer wins)»), 18 раз возвращалась к этому в рассуждениях и с S30 несёт через
все саммари правило «NEVER issue parallel Edit calls to the same file». Это правило затем превратило
26 правок в `node.rs` в 26 последовательных ходов (16:35: «Given the one-edit-per-file-per-turn
constraint»). Воспроизведено в сессии `78844fda`: три параллельных Edit в один файл — осталась одна. И ещё раз —
при написании этого аудита (сессия `411b97d1`): пять параллельных Edit в `DESIGN-long-running.md` одним ходом, все
пять ответили «replaced 1 occurrence», на диск дошла одна (последняя). Дефект воспроизводится стабильно.

**Код.** `fileops.Edit` (`harness/fileops/fileops.go:187`): `os.Stat` → `os.ReadFile` → `strings.Replace` →
`replaceFile` (tmp+rename). Атомарен только сам rename; между чтением и записью никакой блокировки. Файловая
операция запускается на compute-примитиве (`harness/operation/file.go`), т. е. две операции идут
параллельно. Проверки «файл изменился после Read/с момента чтения» нет.

**Последствия.** Потеря данных без сигнала ошибки — худший класс дефекта тула. Плюс вторичный ущерб:
правило «одна правка на файл за ход» убивает параллелизм на самом дорогом ресурсе (ход ≈ 180k токенов).

**Решение.** Любое из:
- мьютекс по абсолютному пути (после `EvalSymlinks`) внутри процесса раннера на `Edit`/`Write`/`apply_patch`;
  операции ставятся в очередь, результат — после реального применения;
- или compare-and-swap: Edit переносит `old_string` на актуальное содержимое заново (он это уже делает —
  проблема только в одновременности), поэтому достаточно сериализации;
- как делает Claude Code: разбивать вызовы одного ответа на батчи по `isConcurrencySafe(input)` —
  read-only параллельно, мутирующие последовательно (§7.3). У нас это естественно ложится на
  `scheduleToolCall`: мутирующие файловые операции одного пути — в один compute-примитив по очереди.

### 2.2. Thinking остаётся в контексте целиком

**Факты.** Прирост входа между соседними ходами совпадает с «весь вывод модели + результаты тулов»
(медианная ошибка 256 токенов), а не с «вывод минус thinking» (475). На момент каждой компакции
собственный вывод модели — 33 % контекста (медиана), thinking — 23 % (~72k из ~300k). За сессию 4,36 M
thinking-токенов, 62 % всех output-токенов; каждый из них потом ещё перечитывался до компакции.

**Почему.** Документация Anthropic (platform.claude.com/docs/en/build-with-claude/thinking, раздел
«Thinking block preservation by model»): *«Keep all prior turns: Claude Opus 4.5 and later Opus models,
Claude Sonnet 4.6 and later… previous thinking blocks remain in context, count toward the window, and are
billed as input tokens»*. Старые модели вырезали thinking прошлых ходов сами — на Opus 5.5 этого нет.
Плюс в автономном режиме вся 20-часовая работа — один «assistant turn» без user-сообщений, так что даже
на старых моделях ничего бы не вырезалось. Харнес шлёт все reasoning-items назад (`keepThinking := true`,
`anthropic/client.go:165`), что правильно для подписей, но не управляет их сохранением.

**Решение.** Серверный `context_management`:
```json
{"edits":[{"type":"clear_thinking_20251015","keep":{"type":"thinking_turns","value":2}}]}
```
с бета-заголовком `context-management-2025-06-27`. Применяется до токенизации, после поиска по кэшу;
клиентская история не меняется. Цена — инвалидация кэша в точке очистки (а не каждый ход): нужно
подбирать `keep`. На Opus 5.5 / Fable 5.1 / Sonnet 5.5 серверная очистка «never invalidates thinking
blocks». Альтернатива без беты — самим не слать Raw у reasoning-items старше последнего ответа
(документация: «outside tool use, omit prior turns' thinking» разрешено) — но в tool-loop это
рискованно для подписей, серверный путь предпочтительнее. Отдельно: для механических правок режим `max`
не нужен — `high`/`medium` на 26 правок `node.rs` сэкономил бы часы (ходы с thinking > 10k идут 150 с).

### 2.3. Компакция как единственная память

**Факты.**
- 57 компакций, 2,13 ч чистого времени, ~0,96 M output-токенов только на саммари.
- Состав тела саммари (по заголовкам шаблона): «Key technical concepts» 44 %, «Files and code» 25 %
  (+2 % «this segment»), «All user messages» 3,9 %, «Pending tasks» 3,2 %, «Current work» 2,6 %,
  **«Problem solving» 4,1 %**, «Next step» 1,6 %.
- Удержание ключевых улик по 56 саммари: «Ladybird проходит CF» — только S2 (в остальных «Ladybird» —
  это guard-правило «don't import Ladybird»); общий cookie jar — 10/56; `hardwareConcurrency` — 1/56;
  «PoW» — 4/56; «воркеры последовательны» — 38/56, но с разрывом S3–S10 и потом «deferred: huge».
- Модель построила себе память сама: `/tmp/summary_prev.txt` (склейка саммари, 88 КБ) — 22 открытия,
  иногда целиком (~25k токенов); 98 вызовов `TranscriptSearch` по собственному прошлому.
- Семь саммари подряд (01:49–03:35) фиксируют «research complete / final pre-implementation pass» при нуле
  строк кода; 8 сегментов без действий.
- Переориентация после компакции — медиана 11,5 вызовов до первого действия.

**Код.** `prompts/compaction.md` — универсальный шаблон в духе Claude Code (9 секций), который поощряет
инвентарь файлов/строк (устаревает после первой правки) и не имеет раздела «гипотезы → улики →
эксперимент → статус», переносимого дословно. `compacted.md` + `compactedMessage` указывают на сырой jsonl
(152 МБ, строки с base64) — модель вынуждена парсить его python-скриптом. Нет: файла заметок/плана, который
харнес сам вставлял бы после саммари; цепочки предыдущих саммари в доступной форме; «не-компактируемого»
слота для правил (ср. запрос к Codex, §7.5). `keptInputs` сохраняет сообщения пользователя дословно —
это хорошо, но пользовательских сообщений за 20 ч было одно.

**Решение.** Три слоя:
1. **Файл состояния, который переживает компакцию.** Как в Anthropic «Effective harnesses for long-running
   agents» (§7.1): `progress`-файл + структурированный список целей/гипотез (JSON — модель реже его портит)
   + коммиты. Харнес: (а) выдаёт в системный промпт/после саммари содержимое `.harness/notes.md`
   (или аналогичного файла воркспейса), если он есть; (б) в промпте компакции требует обновить его
   *перед* тем, как писать саммари (компакция — turn без тулов, значит нужен отдельный шаг «pre-compaction
   checkpoint»: харнес за N токенов до порога шлёт системное напоминание «обнови notes, закоммить»).
2. **Шаблон компакции под долгую инженерную задачу**: обязательный раздел «Hypotheses / evidence / negative
   results / deferred (with cost)» с правилом «переносится дословно, пока не закрыт»; лимит на инвентарь
   файлов; ссылка на notes-файл; «what the indicator showed on the last live run».
3. **Доступ к прошлым саммари**: харнес и так их хранит в сессии — отдать их как
   `TranscriptSearch --summaries` или файл `summaries.md`, а не заставлять парсить jsonl.

### 2.4. Pruning не вытягивает, компакция триггерится выводом модели

**Факты.** Падение входа внутри сегмента > 20k (единственный наблюдаемый след prune) — 8 раз за 22 ч,
каждый на ~120–140k. При этом порог компакции (300k) достигался 57 раз. Доля tool-результатов на момент
компакции по сырым размерам ~65 %, вывода модели — 33 %.

**Код.** `prune.go`: бюджет = 40 % от `AutoCompactTokens` (120k) **только по tool-результатам**, цель —
срезать до 60k, `Keep=12`, `Bytes=600`. Reasoning и сообщения модели не прунятся никогда; картинки — только
в составе результата. То есть при thinking ≈ 72k + саммари ≈ 20k + собственный текст ≈ 30k на сегмент
tool-результатам остаётся ~180k, бюджет 120k достигается редко, и компакция приходит раньше, чем prune
успевает что-то сделать.

**Решение.** (а) Серверный `clear_tool_uses_20250919` (`trigger`, `keep`, `clear_at_least`,
`exclude_tools`) — бесплатен по коду и дружелюбен к кэшу; (б) если оставлять клиентский prune —
считать бюджет по всему контексту и включать reasoning; (в) порог 300k для задачи, где каждый сегмент —
«перечитать 3 файла Firefox», слишком высок: `AutoCompactTokens` ≈ 150–200k с хорошей памятью (2.3) дешевле,
чем 300k с плохой. Anthropic в серверной компакции по умолчанию триггерит на 150k.

модель пишет: «called grace_Read without its full prefix and had to correct it to
mcp__assault_kidney__grace_Read». Логи CLIProxyAPI (`~/Library/Application Support/kou-conveyor/cliproxy/logs`)
подтверждают: шлюз отдаёт модели тулы под именами `mcp__assault_kidney__<слово>_<Tool>` (маскировка под MCP-тулы
Claude Code для OAuth-аккаунтов) и переводит обратно; когда модель срезает `mcp__assault_kidney__`, шлюз
пропускает имя как есть, а `registry.Resolve` требует точного совпадения.

**Решение.** В `Resolve` (или в адаптере) — нормализация: срезать `mcp__<server>__` и известный
`<word>_`-префикс, если остаток — зарегистрированное имя; при неизвестном имени возвращать в ошибке список
доступных тулов (это уже предлагалось в `harness-gaps-analysis/REPORT.md §8`). Параллельно — проверить,
нет ли в CLIProxyAPI настройки отключения переименования (в CLIProxyAPIPlus есть коммиты «Fix Claude OAuth
tool name mapping», «Add reverse mappings for original tool names»).

### 2.6. Нет бюджета, стоп-условия и отчётности

**Факты.** Задача №4 — две цели в одном сообщении: безграничная («отпечатки как у Firefox») и бинарно-непрозрачная
(«managed-probe → 200»). Преамбула: «Treat the prompt as a goal and keep working until it is met». Результат —
20,2 ч без остановки, 4 152 хода, 9,2 M output-токенов одного подписочного аккаунта; за это время 147 видимых сообщений медианой 74 символа («Now the
edits…»), все три содержательных отчёта (> 400 символов) относятся к задачам №1–3. Критерий успеха молча
переписан внутри саммари (00:37–08:06: «200 without interactiveBegin»; с 14:41 «interactive checkbox
acceptable»). Чекпоинтов нет: один незакоммиченный дифф на ~30k строк (при этом харнес сделал 680 снимков
дерева в `.changes/repo.git` — модель о них не знает и использовать не может).

**Код.** `coordinator.Dependencies` знает `AutoCompactTokens`, `ToolHeartbeatInterval`, `ToolGrace`; нет
`MaxTurns`, `MaxTokens/Cost`, `MaxWallClock`, `MaxCompactions`, `ReportEvery`. Единственный выход из
`when_idle` — модель сама не вызывает тулы.

**Решение.** Claude Agent SDK даёт `max_turns`/`max_budget_usd` с результатом `error_max_*` (§7.3) — у нас
нужен тот же класс ограничителей на уровне `Dependencies` + поведенческий: каждые N компакций (или часов)
харнес вставляет системное сообщение «напиши пользователю отчёт: проверено / подтвердилось / отвергнуто /
план, затем продолжай», а по исчерпании бюджета — «итоговый отчёт и стоп». Anthropic отдельно отмечает,
что Opus 5.5 / Fable 5.1 «write fewer progress updates at higher effort and in long tool chains» и
рекомендует явно просить user-facing progress updates — т. е. отчёты без принуждения не появятся.

### 2.7. Нет детектора зацикливания

**Факты.** `gfxFont.cpp` — 74 чтения в 14 сегментах; `gfxTextRun.cpp` — 68/12; `host_surface.rs` — 64+33
чтений; всего 2 356 чтений 552 файлов. 6 сегментов без действий, 7 саммари подряд с «research complete».
Текстовый движок: ~3 ч чтения до первого файла. Это паттерн OpenHands «repeating action-observation cycles» /
«agent monologue» (§7.2), только растянутый компакциями: детектор на уровне одного контекста его не
увидит — нужен счётчик по всей сессии.

**Решение.** Сессионный счётчик повторов (по нормализованным аргументам Read/Bash) с мягким вмешательством:
на N-м чтении того же файла в новом сегменте — системная вставка «этот файл читался N раз в K сегментах;
запиши выводы в notes и действуй»; для «сегмент без действий» — то же после компакции. Жёсткая остановка
(как в OpenHands) — опционально по порогу.

### 2.8. Один вызов на ход и цена хода

**Факты.** 79,2 % ходов — один вызов (3 290 из 4 152), среднее 1,29. Медиана латентности 6,5 с, но ход
означает перечитывание 181k токенов (медиана) из кэша. 83 команды со `sleep` (поллинг вместо ожидания
результата — в той сборке плейсхолдер «still running» ещё не давал путей к `out`/`err` и команды `kill`;
сейчас даёт).

**Решение.** В основном модельное поведение, но харнес может: (а) показывать стоимость в плейсхолдере/в
heartbeat («this turn re-read 181k tokens»), (б) settle-window 3–5 с вместо 1 с (`toolCallRunGracePeriod`),
чтобы результаты параллельных вызовов приходили одним ходом (предлагалось в REPORT.md §5), (в) для
`max`-режима — прямое указание в преамбуле, что одиночный вызов за ход на 300k контекста — ошибка.

### 2.9. Прочее, замеченное по пути

- **Запрос компакции с картинками → HTTP 413.** В логах шлюза 30.09 20:50 UTC — запрос на 34,6 МБ с
  74 изображениями и 0 тулов (компакция). `fit()` режет только когда оценка > бюджета, а `imageTokens=1600`
  занижает картинку в 3–4 раза; размер тела в байтах вообще не контролируется. Лимит Anthropic по телу —
  32 МБ. Нужна отдельная отсечка по байтам/числу картинок для запроса компакции.
- **Session-файл 152 МБ за 22 ч**: 29 227 записей операций на 5 315 операций (каждая смена фазы `awaiting`
  — отдельная запись с полным state), плюс `logs/20260930-212652.jsonl` 73 МБ — полная копия в воркспейсе.
  Upstream сделал логи opt-in (§8). `TranscriptSearch` по такому файлу работает, но саммари указывает модели на
  него как на «источник деталей» — это тупик.
- **Read без ограничения по байтам**: медиана 5,1k символов, p90 20,5k, max 83k (целиком `values.rs`,
  `layout.rs`, `summary_prev.txt`); лимит только по строкам (2000). Codex ограничивает tool output
  токенами (`tool_output_token_limit`, по умолчанию 12k).
- **Правило «не выдумывать якоря searchfox» и аудит якорей 15:28–16:03** — следствие того, что у модели нет
  инструмента «процитируй источник», но это вне харнеса.
- **Shell**: 3 099 команд, 42 с ненулевым кодом, 1 таймаут, 15 упёрлись в 40k-лимит вывода — нормально.
- **Heartbeat ни разу не сработал** — все тулы завершались < 10 мин. Хорошо, но и 10-минутные паузы при
  тестах никто не ловил бы: heartbeat только для висящих тулов, не для «модель молчит 20 ч».

### 2.10. Лимиты подписки: не измеряются, не планируются, при упоре — смерть run-а

**Контекст.** Модель ходит через локальный шлюз CLIProxyAPI по OAuth-аккаунтам подписок (Claude Max, Antigravity,
xAI), не по платному API. Поэтому «стоимость в долларах» (§1, §2.6 в первой редакции) — не та единица: значимы
**окна лимитов** — скользящее 5-часовое и недельное, на Max планах с отдельными бакетами для Opus и Sonnet, у
Fable — своим; формулу расхода Anthropic не публикует.

**Факты.** Всю сессию обслужил один Claude-аккаунт: 4 923 запроса за 22 ч, 830 M cache-read, 24,5 M
cache-write, 9,16 M output (5,96 M reasoning), 9 сетевых сбоев (connection reset / EOF / 413), **0 упоров в
лимит** (`cliproxy/usage.json`, логи ошибок шлюза). Сколько это съело недельного Opus-окна — **неизвестно**:
cockpit умеет спрашивать `https://api.anthropic.com/api/oauth/usage` (`accounts.fetchClaude`: utilization % и
`resets_at` по окнам `five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, Fable, `weekly_scoped`,
`extra_usage`), но делает это только по запросу из UI, держит 3 минуты в памяти и никуда не пишет. Семь ночных
часов «текстового движка» без единого живого прогона (01:05–07:18) — это часы недельного Opus-окна, которые до
сброса не вернутся и которых утром не будет у пользователя.

**Код при упоре в лимит.** `harness/llm/clients/anthropic/client.go`: 429 → `retry-after` (обрезан до 1 мин)
или backoff ≤ 30 с, не более `DefaultRemoteMaxAttempts = 5` попыток → ответ-Failure; `coordinator/loop.go`
`maxFailures = 2` → третий Failure подряд завершает run с ошибкой. Итого `when_idle`-сессия **умирает через
несколько минут** после достижения 5h-окна, хотя сброс может быть через 5 ч. Шлюз при этом держит аккаунт в
`StateCooling` с `RetryAt` — раннер этого состояния не читает. Claude Code с v2.1.234 в той же ситуации ждёт в
сессии и продолжает сам после сброса (фиксированным промптом, re-arm ≤ 2 раз подряд).

**Решение.** (а) Снимки `Quota.Windows` по аккаунтам раз в 10–15 мин в историю + utilization на старте/компакции/
rollover/финише сессии в её журнал — без этого бюджет не измерим; (б) состояние `waiting_for_quota` в
координаторе: пауза до `resets_at`/`RetryAt` вместо смерти, затем «продолжай с места остановки», для weekly —
отчёт и вопрос пользователю; (в) бюджет автономного режима в единицах окон (резерв 5h для пользователя, доля
weekly·Opus), а не токенов/долларов; (г) маршрутизация ролей по окнам: Sonnet/Haiku-роли не тратят Opus-окно,
другой провайдер — другая подписка. Подробно — `DESIGN-long-running.md` §3.1.

## 5. Что харнес сделал правильно на этой сессии

- **Устойчивость.** 22 ч без падений, 4 209 ходов, 57 компакций — ни одной неудачной (кроме оборванной
  извне), ни одного `Failure`, ни одного heartbeat; 97,4 % входа из кэша (стабильный префикс, брейкпоинты).
- **Append-only store + операции** позволили сделать этот аудит с точностью до секунды и байта: все
  команды, результаты, thinking, usage сохранены; `TranscriptSearch` реально помогал модели (98 вызовов).
- **Файловые тулы** (Read с нумерацией, Edit с подсказками «whitespace/first line matches», atomic write) —
  7 отказов на 2 204 операции, все с внятной диагностикой.
- **Асинхронные тулы и плейсхолдеры**: модель корректно «засыпала» на сборках вместо ожидания в цикле (когда не
  поллила `sleep`).
- **Снимки дерева** (`.changes`, 680 снапшотов) — есть основа для чекпоинтов/отката, просто не выведена модели.
- **Сохранение пользовательских сообщений дословно** при компакции — цель задачи не искажалась (искажался
  критерий успеха, который пользователь не формулировал).
- Инфраструктурные ретраи и обработка overflow (`recoverFromOverflow`, `fit`) — не понадобились, но есть.

## 7. Как с этим борются другие

### 7.1. Anthropic: «Effective harnesses for long-running agents» (нояб. 2025) и «Harness design…» (март 2026)
Источники: anthropic.com/engineering/effective-harnesses-for-long-running-agents;
jinyansu1.github.io/blog/2026/07/agent-context-engineering-long-running-harness; ruh.ai/blogs/anthropic-3-agent-harness-design.

- Две типовые поломки, обе есть у нас: *one-shot* (сделать всё сразу, упереться в контекст посреди фичи) и
  *declare victory early* (или, в нашем варианте, «research complete» без кода).
- Решение v1: **initializer agent** (другой промпт для первого контекстного окна) создаёт `init.sh`,
  `claude-progress.txt`, **feature_list.json** (все пункты `passes:false`; JSON, потому что модель реже портит
  JSON, чем Markdown; «unacceptable to remove or edit tests»), первый git-коммит. **Coding agent** в каждом
  окне: `pwd` → прочитать progress + git log → smoke-тест через `init.sh` → одна фича → коммит + запись в
  progress. Дословно: «compaction isn't sufficient… doesn't always pass perfectly clear instructions to the
  next agent».
- v2 (март 2026): **planner / generator / evaluator**: evaluator независимо проверяет результат (Playwright)
  и отклоняет; «sprint contract» перед каждой фичей. Вывод авторов: scaffolding должен ослабляться по мере
  роста моделей, но файл состояния + коммиты + внешняя проверка остаются.
- Применимость: наш `when_idle` — это ровно «coding agent без initializer». Нужны: стартовый шаг, создающий
  план/гипотезы в файле; обязательный коммит на фичу; требование живого прогона (у нас в
  `docs/worker-agent-plan.md:40` это уже написано, но харнес не следит).

### 7.2. OpenHands: StuckDetector и condensers
Источник: docs.openhands.dev/sdk/guides/agent-stuck-detector; github.com/OpenHands/software-agent-sdk (…/conversation/stuck_detector.py).

- Пять паттернов: одинаковые action→observation ×4; action→error ×3; монолог ×3; чередование двух пар ×6;
  повторные ошибки контекстного окна. Сравнение — по семантике (имя тула + аргументы + текст), не по id.
  Включён по умолчанию, может остановить run. У нас аналог должен считать по всей сессии (сквозь компакции).
- Condensers (LLMSummarizing, observation masking) — аналог нашего prune/compaction; важно, что они
  настраиваются как pipeline, а не одним порогом.

### 7.3. Claude Code / Claude Agent SDK
Источники: platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use; разборы исходников Claude Code
(x.com/spandan_madan/article/2067320100911493454; github.com/alejandrobalderas/claude-code-from-source ch07);
augmentcode.com/guides/claude-agent-sdk-agent-loops-tool-calls; harnez.ai/posts/inside-the-agent-loop.

- **Партиционирование вызовов одного ответа**: `isConcurrencySafe(input)` на каждый вызов; Read/Glob/Grep и
  read-only Bash — параллельно, Edit/Write/мутирующий Bash — последовательно, в порядке модели. Это ровно
  лекарство от §2.1 без запрета параллельности.
- **Ограничители**: `max_turns`, `max_budget_usd` → `error_max_turns` / `error_max_budget_usd`; `effort`.
  По умолчанию не заданы — авторы гайдов называют это главной ошибкой для unattended-запусков. Нужен наш
  аналог в `Dependencies` + env.
- **Память**: CLAUDE.md / auto-memory, `/compact` с фокусом, компакция по порогу; thinking прошлых ходов на
  Opus 4.5+ сохраняется — Claude Code живёт с этим за счёт user-turn границ, которых у автономного `when_idle` нет.

### 7.4. Anthropic Messages API: серверное управление контекстом
Источники: platform.claude.com/docs/en/build-with-claude/context-editing; …/thinking; …/compaction-threshold.

- `clear_thinking_20251015` — `keep: {thinking_turns: N} | "all"`; **прямое решение §2.2**.
- `clear_tool_uses_20250919` — `trigger`, `keep`, `clear_at_least`, `exclude_tools`, `clear_tool_inputs` —
  серверный аналог нашего prune, «applied before the prompt reaches Claude», кэш инвалидируется только в
  точке очистки; **решение §2.4**.
- `compact_20260112` — серверная компакция по порогу (по умолчанию 150k, минимум 50k), `instructions`
  заменяет промпт целиком, `pause_after_compaction`; клиент просто дописывает ответ с `compaction`-блоком.
  Снимает с нас 2,13 ч/0,96 M токенов компакций и риск 413, но лишает контроля над шаблоном (частично
  компенсируется `instructions`). Все три — бета `context-management-2025-06-27` (`compact-2026-01-12`).
- Memory tool (`memory_20250818`) — файловая память, которой управляет модель; у нас это может быть просто
  файл в воркспейсе, который харнес гарантированно показывает после компакции.
- Отдельно из документации по thinking: Opus 5.5 / Fable 5.1 «write fewer progress updates at higher effort
  and in long tool chains» — отчётов надо требовать явно.

### 7.5. OpenAI Codex CLI
Источники: codex.danielvaughan.com/2026/03/31/…compaction-architecture и …/2026/04/16/…tuning-long-sessions;
community.openai.com/t/experimental-context-management-compaction-in-codex/1395578; github.com/openai/codex/issues/27130.

- Компакция в двух точках (до user-turn и на границе tool-loop), `tool_output_token_limit` (12k по умолчанию,
  советуют 8k), **AGENTS.md перечитывается после компакции** — «critical information that must survive
  compaction belongs in AGENTS.md, not in conversation history».
- Codex 0.153.4 (сент. 2026): экспериментальный режим из трёх частей — **token budget**, **history & notes**
  (важное сохраняется, старое извлекается по запросу), **`new_context`** (модель сама начинает свежее окно,
  опираясь на notes). Мотивация дословно наша: «no longer has to rely only on repeated summaries, which can
  lose details over time».
- Issue #27130: просьба о «small non-compactable preflight rule slot» — минимальном контракте исполнения
  (проверить состояние задачи, working tree, evidence of completion), который не проходит через компакцию.
  У нас такой слот напрашивается для правил вроде «после каждой фичи — живой прогон».

### 7.6. Ralph loop (Huntley; snarktank/ralph)
Источники: leanware.co/insights/ralph-wiggum-ai-coding; github.com/snarktank/ralph.

- Каждая итерация — свежий контекст; память только через git history, `progress.txt`, `prd.json`
  (`passes`); Stop Hook перезапускает промпт. Крайняя форма «не доверяй саммари»: доверяй файлам и коммитам.
  Для нас — аргумент в пользу `new_context`-подобного режима: после N компакций без движения индикатора
  начать заново с notes и git log, а не с 57-го пересказа пересказа.

### 7.7. Имена тулов через прокси

name mapping», «Add reverse mappings for original tool names»); github.com/router-for-me/CLIProxyAPI/issues/1530.

## 9. План работ (приоритеты)

### P0 — устраняют потерю данных и прямые убытки
1. **Сериализация мутирующих файловых операций по пути** (`fileops`/`operation/file.go` или партиционирование в
   `scheduleToolCall` по признаку read-only). Тест: три параллельных Edit в один файл → все три применены.
2. **`context_management` в Anthropic-клиенте**: `clear_thinking_20251015` (`keep: 2–3 turns`) +
   `clear_tool_uses_20250919` (`trigger ≈ 100k`, `keep ≈ 10`, `clear_at_least ≈ 20k`, `exclude_tools: [Edit, Write]`),
   конфигурируемо через env; клиентский prune оставить как fallback для других провайдеров.
3. **Алиасы имён тулов** в `registry.Resolve` (срез `mcp__*__` и `<word>_`), в ошибке — список доступных.
4. **Бюджет автономного режима в единицах окон подписки** (§2.10, DESIGN §3.1), а не в долларах/токенах:
   - раннер пишет снимки `Quota.Windows` (utilization %, `resets_at`) по аккаунтам раз в 10–15 мин в
     `quota-history.json` и в журнал сессии на старте/компакции/rollover/финише — иначе бюджет не измерим;
   - в `Dependencies`/env: `UsageReserve5h` (сколько % 5h-окна оставить пользователю, по умолчанию ~15),
     `UsageWeeklyOpusMaxShare` (доля weekly·Opus на эту цепочку, ~60) плюс технические стоп-условия
     `MaxCompactions`/`MaxWallClock` как страховка; при достижении — системное сообщение «итоговый отчёт и стоп»,
     затем `when_idle` снимается;
   - **при упоре в лимит (429 / `StateCooling`) — не смерть run-а, а состояние `waiting_for_quota`**: пауза до
     `resets_at`/`RetryAt` шлюза, затем «продолжай с места остановки» (re-arm ≤ 2 раз подряд, как в Claude Code);
     для недельного окна — отчёт и вопрос пользователю, а не ожидание сутками;
   - роли, которым хватает Sonnet/Haiku (судья, pruning, саммари), не тратят Opus-окно (§7.3).

### P1 — память и управление целью
5. **Файл состояния, переживающий компакцию**: харнес вставляет `.harness/notes.md` (или настраиваемый путь)
   после саммари; за ~30k токенов до порога — системное напоминание «обнови notes и закоммить»; в
   `compaction.md` — раздел «Hypotheses / evidence / negative results / deferred (cost)», переносимый
   дословно; лимит на инвентарь файлов; ссылка на notes вместо сырого jsonl.
6. **Принудительные отчёты**: каждые N компакций/часов — вставка «краткий отчёт пользователю: что проверено,
   что подтвердилось, что отвергнуто, следующий эксперимент». Явно, потому что Opus 5.5 на `max` сам отчётов не пишет.
7. **Детектор повторов по всей сессии** (нормализованные Read/Bash-аргументы; «сегмент без действий»): мягкая
   системная вставка, при пороге — стоп с отчётом.
8. **Чекпоинты модели**: показать модели `.changes`-снимки (команда «что изменилось с компакции N») или
   просить коммит на фичу в ветку сессии; это даёт bisect, которого не было.

### P2 — экономика и гигиена
9. Settle-window 3–5 с вместо 1 с; стоимость хода в плейсхолдере/heartbeat.
10. Порог компакции для 1M-моделей ≈ 150–200k при наличии notes-файла; отсечка компакционного запроса по
    байтам/картинкам (защита от 413).
11. Read: лимит по байтам (например, 40k символов, как у Bash) с подсказкой offset/limit; `summary_prev`-подобные
    файлы модель не должна читать целиком.
12. Опциональный `-log-directory` (как в upstream #9); сжатие `awaiting`-записей операций в store.
13. Суб-агент «исследование» (из REPORT.md §9): чтение исходников Firefox в отдельном контексте с возвратом
    резюме — структурно убирает петлю «прочитал → компакция → перечитал».

### Отдельно — для пользователя, запускающего такие задачи
- Одна метрика + тайм-бокс в самом промпте («managed-probe → 200 за 4 часа, иначе отчёт и стоп»);
  `high` вместо `max` для реализационных фаз; явная просьба вести файл гипотез — до того, как это
  появится в харнесе.
