# kou-conveyor harness: пробелы, влияющие на качество работы модели

Анализ кода `harness/` + эмпирика по 29 реальным сессиям из `.harness/sessions`
(скрипты в `scripts/`).

## 0. Модель стоимости (из данных)

| Метрика | Значение |
|---|---|
| Сессий / ответов модели / tool-вызовов | 29 / 3 627 / 4 596 (Bash 4 332, ViewImage 263) |
| Сообщений пользователя | 78 (≈46 ответов модели на одно сообщение) |
| Input-токенов всего / из кэша | 1.50 млрд / 1.48 млрд (98.7 % cached) |
| Output-токенов всего | 6.7 млн |
| Размер запроса: медиана / p90 / max | 386k / 745k / 998k токенов |
| Доля запросов > 200k токенов | 76 % (на них уходит 94 % всех input-токенов) |
| Компакций за все сессии | 2 |
| Латентность модели: медиана / p90 | 11 с / 44 с |

Вывод: стоимость и качество определяются **числом ходов × размером контекста**, а не
output-токенами (cached-input в ~20 раз больше output даже с учётом цены).
Каждый лишний ход (ошибка zsh, «пустое» пробуждение, polling через sleep) — это
повторное чтение 400–900k токенов + ~11–20 с. Все рекомендации ниже оцениваются через эту призму.

## 1. Только Bash для работы с файлами (Edit/Write/Read или apply_patch)

**Факты из сессий:** ~1 540 heredoc'ов (медиана 32 строки, p90 193, максимум 1 292 строки файла,
протащенного через shell); 934 правки через `python3 - <<EOF` / `python3 -c`, из них 730 —
эмуляция search/replace; 61 `sed -i` (≈11 падений на BSD sed macOS); 85 heredoc'ов
с незакавыченным разделителем, из них 57 с `$`/backtick внутри содержимого (тихая порча файла).

**Что это даёт модели:** каждая правка = каркас Python/heredoc + экранирование + отдельный ход
на перечитывание результата; ошибки не структурированы («old_string not unique» нет);
параллельные правки одного файла не сериализуются (нашёл 1 такой случай).

**Предложение:**
- Инструменты `Read` (offset/limit, нумерация как в `linked.go/writeLines`, guard на размер/бинарники),
  `Edit` (old_string→new_string, проверка уникальности, `replace_all`, нормализация CRLF/отступов)
  и `Write`; либо `apply_patch` (V4A формат Codex). Диалект выбирать по семейству модели —
  `SetTools` уже позволяет менять набор на лету.
- Результат `Edit` возвращает фрагмент ±5 строк с номерами (экономит ход на перечитывание);
  опционально — синтаксическая проверка по расширению (gofmt -l / py_compile).
- Guard «файл изменился после чтения» (mtime) и сериализация правок одного пути.
- Реализация: (а) дешёвый путь — command-tool во встроенном плагине `core`
  (`tool/command` уже передаёт JSON-аргументы на stdin); (б) нативно — операция `file_edit`
  + примитив `io.write` (atomic tmp+rename) рядом с `io.create`/`io.read`.

## 2. Гигиена контекста: pruning старых результатов + более ранняя компакция

**Факты:** медианный запрос 386k, компакций 2 на 29 сессий. Порог автокомпакции —
`window − min(33k, window/4)` → для 1M-моделей 967k. Результаты `grep`/`sed -n`/`go test`
(1 736 + 1 135 + 809 вызовов) и base64-картинки (263) живут в контексте вечно.

**Предложение:**
- «Микрокомпакция» в `contextbuilder` без вызова LLM: при `EstimatedTokens > порога` заменять
  tool-результаты старше последних K ходов (или сверх скользящего бюджета, напр. 60k токенов
  tool-output) заглушкой `[N байт вырезано; полный вывод: <OutPath>]`, картинки — заглушкой.
  Делать пачками, чтобы префикс кэша менялся редко (одна перезапись кэша на пачку).
- Дефолт `AutoCompactTokens` для окон ≥ 400k ограничить (напр. 50 % окна или ~250k) — качество
  рассуждений падает задолго до 900k.
- После компакции: секция «недавно прочитанные/изменённые файлы» (появится при наличии
  Read/Edit) и опционально авто-подгрузка последних из них.
- Указатель на «сырой» JSONL-транскрипт (`compactedMessage`) практически бесполезен: файлы
  4–38 МБ, строки по мегабайту с base64. Нужен `TranscriptSearch` (tool или подкоманда runner'а),
  возвращающий читаемый текст с контекстом.
- `imageTokens = 1600` занижает оценку: 2000×2000 у Anthropic ≈ 5.3k токенов.

## 3. Shell: инструмент называется Bash, а запускается `$SHELL` (zsh на macOS)

**Факты:** 78 результатов с ошибками `zsh:`: 65 × `no matches found` (`grep --include=*.go`,
глобы без совпадений), `===== not found` (zsh-расширение `=cmd`), `timeout: command not found`,
BSD `sed -i`. Каждая — потерянный ход (~11–20 с + чтение всего контекста).
Причина второго класса ошибок — системный промпт утверждает «isolated sandbox container»,
а сессии идут на macOS разработчика: модель предполагает Linux/GNU.

**Предложение:** запускать `bash` при наличии (иначе `sh`), сделать настраиваемым;
env-блок в системном промпте (~150 токенов, кэшируется): ОС/арх, shell, cwd, git-ветка/статус,
дата, наличие `rg`/GNU-утилит; не заявлять изоляцию, если её нет (флаг runner'а).

## 4. Bash: нет timeout, нет отмены, нет доступа к прогрессу

**Факты:** `validateArguments` принимает только `command` и `max_output_length`. Зависшая команда
держит шаг вечно; heartbeat каждые 10 мин будит модель (полное чтение контекста), а убить процесс
она не может — PGID не показывается, `Manager.Cancel` не выведен в tool. 279 вызовов с `sleep N` —
polling за неимением способа посмотреть частичный вывод.

**Предложение:**
- Параметр `timeout` (дефолт ~10 мин, TERM→KILL, в результате пометка «timed out» + хвосты out/err).
- В placeholder «still running» включать пути `out`/`err` (известны из `newShellPaths` до старта) —
  модель делает `tail`, а не `sleep`; и/или tool `Cancel(call_id)`.
- В результат добавлять длительность («took 32 s») — калибрует ожидание/параллелизм.
- Backoff для heartbeat (10 → 20 → 40 мин) при отсутствии изменений.

## 5. Слипание пробуждений (settle window)

**Факты:** 857 из 3 660 ходов (23 %) начались с placeholder'ами (1 157 шт.). В 140 из них все
висевшие вызовы завершились **до того, как модель ответила** (медиана 3.5 с после старта хода,
p90 13.9 с), ещё в 60 — часть. Т.е. ~23 % таких ходов — рассуждение на устаревшем состоянии
и сразу следующий ход. Grace-период фиксирован: `toolCallRunGracePeriod = 1 s`.

**Предложение:** debounce — в `finishToolCall`, пока в `stepCalls` есть другие живые вызовы,
перезапускать `grace` (напр. 5 с) с верхней границей (напр. 15 с от первого результата);
внешний ввод «at once» обходит окно. Настраиваемо через `Dependencies`. Цена — секунды латентности,
выигрыш — ~100–150 ходов на 29 сессий и меньше решений на неполных данных.

## 6. Stop reasons и пустые ответы не обрабатываются

**Факты:** в `coordinator/loop.go` нет ни одного обращения к `response.Stop`/`response.Failure`
(кроме overflow). `StopMaxOutputTokens` без tool-вызовов → сессия завершается обрезанным текстом;
`StopRefused` (3 случая) и пустой output (3 случая) → сессия молча уходит в idle.

**Предложение:** `max_output_tokens` без вызовов → авто-«continue» (один раз); refusal/пустой ответ →
одна повторная попытка с пометкой, затем явное сообщение пользователю; `Failure` → ошибка наружу.

## 7. «Ворота завершения» — качество за +1 ход

Сейчас ход без tool-вызовов при пустой очереди = конец сессии, без проверки. Варианты:
- плагин декларирует `verify: ["go build ./...", "go test ./..."]`; при уходе модели в idle
  команды выполняются, ненулевой код возвращается ей один раз (ограничить N повторов);
- либо self-review ход: «перечитай запрос и `git diff`, проверь каждое требование»;
- либо дешёвый судья (Haiku/mini) по финальному сообщению: «анонсирует действия, но не делает» →
  nudge «continue».
Цена: +1–3 % ходов; ловит «сказал сделано — тесты падают» и недоделанные пункты.

## 8. Промпты и описания инструментов

- Описание Bash — одна строка. Нет: cwd сбрасывается каждый вызов; какой shell; нет интерактивных
  команд; правила кавычек heredoc; как режется вывод; что фоновые процессы убиваются.
- Преамбула: «tool calls are cheap» — верно про вызовы, неверно про ходы; стоит явно сказать «ход дорог,
  батчи вызовы, не поллинг».
- Дефолтный системный промпт (3 строки) без инженерных норм (читай перед правкой, не угадывай API,
  запускай тесты, минимальные диффы, не коммить без просьбы) — самый дешёвый рычаг (~300 токенов).
- Сообщения харнесса (heartbeat, placeholder, steering) идут ролью user без маркировки — модель
  может принять их за волю пользователя; пометить как `[harness]`.
- Поздний результат в Anthropic-адаптере: `"Result of tool call toolu_…:"` — только ID; в контексте
  400k+ сопоставить с командой трудно. Использовать `describeCall` (уже есть) в заголовке.
- «tool %q is not available» — добавить список доступных (был вызов несуществующего `cript`).

## 9. Крупнее: суб-агенты и план

- `Task`/sub-agent: исследование (grep/sed/find — ~3 000 вызовов) в отдельном контексте, в основной
  возвращается резюме. Архитектура операций/remote-jobs позволяет запустить координатор внутри
  операции. Главное структурное средство против роста контекста.
- Tool `Plan`/todo, переживающий компакцию (вставка в системный промпт/после summary): снижает дрейф
  на задачах в 100–300 ходов.

## 10. Приоритеты

Быстрые (дни): bash вместо $SHELL + env-блок; описание Bash и нормы в преамбуле; обработка
Stop/Failure; `describeCall` в заголовках; пути out/err в placeholder; timeout у Bash.
Средние (1–2 недели): Edit/Write/Read (или apply_patch) как command-tool в core; settle window;
микрокомпакция + ранний порог; ворота завершения (verify-хук).
Крупные: суб-агенты; план-инструмент; TranscriptSearch.
